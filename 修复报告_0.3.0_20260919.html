dsh-plugin-npm-manager 修复报告
设置页从"什么都不显示"到端到端跑通

2026-09-19 · 0.2.0 → 0.3.0 · dsh 0.1.5-rc.2 · profile = web · 全部结论均来自本机实测
修好了，并且是真实环境端到端验证的 —— 不是沙箱自测。
Settings → 插件 → 插件配置 里现在能看到「NPM 管理器」卡片， 渲染出 9 行真实包数据（4 个可升级），范围切换与刷新按钮可用，零页面错误、零失败请求。

根因是三层阻断串联，任何一层不修都看不到面板。原来的 31 个测试全绿， 但一条都没覆盖到这三层 —— 这也是本轮把测试从"字符串包含"改成"真调组件 + 真跑浏览器"的原因。

1. 三层阻断（全部已修）

第 1 层 · 挂载插件从未进入 cordis 配置树
patch: entry "npm-manager" not found
第 2 层 · 渲染注册的不是 React 组件
Objects are not valid as a React child
第 3 层 · 注册bundle id 与包名不一致
loaded without registering
第 1 层插件从未被挂载 —— 它连报错的机会都没有

修复前：

$ dsh --profile web --dump-config
dsh: [.../profiles/web/cordis.patch.yml] patch: entry "npm-manager" not found

$ grep -c 'npm-manager' dump.yml   → 0     # 合成树里根本没有它

三处配置同时错，缺一不可：

  1. 插件自带的 cordis.patch.yml 用了顶层 - id:。 applyEntryPatches() 对非 insert 补丁要求 id 命中已存在条目，未命中就 warn + 丢弃， 不创建条目。而且 name 填了 link:./src/index.ts —— 把 pnpm 的依赖协议写进了 cordis 的包名字段。
  2. profile 的 dsh.profile.bundles 没有登记本包 → 本插件的 cordis.patch.yml 根本不会被 apply（bundle 列表才是入口）。
  3. profile 自己的 cordis.patch.yml 里那段 - id: npm-manager 因 id 不存在被静默丢弃。

修法：插件 patch 改 - insert:；包名加进 dsh.profile.bundles； profile 那段保留为"用户层覆盖"（bundle 层先插入，本层后应用，id 此时已存在）。

验证：warn 消失，合成树里出现 - id: npm-manager / name: dsh-plugin-npm-manager。

第 2 层注册的"组件"不是 React 组件

渲染器（dsh-client-ui-renderer/lib/client.js:652）直接：

function renderEntry(slotKey, Comp, kit, ...) {
  return jsx(Comp, { ...kit, ...injected, ...slotInjected.props, ...ownerProps });
}                       // Comp = entry.component，必须是 React 组件

旧代码注册的是一个返回普通对象的函数：

scoped.slots.register(def, function () {
  return { render: function (props) { ... } }   // React 收到一个对象 → 抛错
})

而且组件里读 props.target / props.dom.firstChild —— slot kit 提供的是 t / renderSlot / store 等座位，没有任何 DOM 注入入口， 所以 target 恒为 undefined。

修法：重写为真 React 组件，用 React.createElement 构建 UI， 数据走 fetch('/plugins/npm-manager/...')。

第 3 层bundle 的 id 与包名不一致 —— 这是最隐蔽的一层

dsh-client-modules/lib/client.js:248：

if (!this.factories.has(id))
  throw new Error(`client-modules: bundle ${url} loaded without registering "${id}" via __ModuleLoader__.load`);

这里的 id 是图行 id，即 包名。package.json#name 是 dsh-plugin-npm-manager，而旧产物里写的是 id: 'npm-manager' → 必然抛错。

这一层是在真实浏览器里才暴露的：服务端 --dump-config 全绿、路由全通， 但前端一加载就炸。旁边的社区插件 @changfenhuang/dsh-annotation 源码里正好留了一条注释点明这个坑。

修法：构建脚本从 package.json#name 读 id，不写常量； 并在构建与测试里各加一条断言，杜绝改名后漂移。

附带两处契约偏差
  • locale 传了字典对象。渲染器把 entry.locale 当命名空间字符串用 （localeSeat(face, entry.locale) → face.bind(ns) → dicts.get(ns)）， 传对象不报错，但查不到字典 → t('title') 原样返回 'title'，界面显示裸 key。 改为 locale: NS（字符串）+ ctx.locale.register(NS, {zh, en}) 注册字典。
  • dsh.client.inject 缺 @deepseek-ai/dsh-client-ui-settings —— 那是 settingsScope 的提供方（super(ctx, "settingsScope")）。 对照 dshmarket 声明了 locale + ui-settings + ui-theme。

4. 剩余问题（已定位，本轮未修）

按你指定的范围，本轮只做了"挂载 + 客户端渲染"。以下问题都已实测定位：

4.1全局扫描有两个真缺陷

交互测试里点「全局」显示 0 个包。我没有直接当成 bug —— 先做了对照实验：

# A. 当前环境（本沙箱 shell 里 APPDATA 不存在）
scanGlobalPackages() = []

# B. 补上 APPDATA 后
APPDATA="C:\Users\Admin\AppData\Roaming" node -e "..."
scanGlobalPackages() = [{"name":"opencode-ai","currentVersion":"1.18.30"},
                       {"name":"pnpm","currentVersion":"11.22.0"}]

所以"0 个包"在我的启动环境下是假象（本沙箱 shell 只有 LOCALAPPDATA/USERPROFILE/TEMP， 没有 APPDATA）—— 你正常启动 dsh 时应该能看到 2 个。但暴露了两个真缺陷：

  1. 无兜底：只认 process.env.APPDATA，没有 USERPROFILE / os.homedir() 回退。 任何环境下 APPDATA 缺失就静默返回空。
  2. 永久跳过 scoped 包：src/services/scanner.ts:69 的 if (item.startsWith('@')) continue。本机 4 个全局项里 @colbymchenry、@deepseek-ai 两个永远列不出来，与环境无关。
4.2路由 :name 是死路由

kind:'exact' 的 path 不支持 :param —— exact 表是字面量 Map 查找 （dsh-host-webserver/lib/index.js:322）。该路径永远命中不了，请求落到 SPA fallback。 应改 kind:'prefix'（handler 里已有 regex 解析，可直接复用）。

⚠️ tests/routes-verify.mjs 用 fake webServer 只收集不匹配， 结构上就不可能发现这个问题 —— 和客户端那层一样，是"测试全绿但功能是死的"。

4.3npm_apply_upgrade 永久不可用

guard 读 exec.agent?.approvals?.get?.(exec.callId)?.granted，而官方 ToolExecution 类型是 {callId, rootCallId, name, arguments, agent?, parent?, signal, token} —— 没有 approvals，dsh-agent 包里也搜不到。 granted 恒为 undefined → 工具 100% 被拦，且用户没有任何途径批准。 应改走 ctx.on('tools/pre-execute') + ctx.userQuestions.ask()。

4.4其余
  • 卡片目前只读展示，4 个配置字段还不能在界面上编辑（只能改 profile 的 patch）。
  • RegistryClient.getChangelog 仍返回空数组（GitHub Releases 未接）。
  • vendor 快照仍带 scripts / .archive/ 等冗余（不影响运行）。

7. 一句话总结

面板不显示，是挂载层、渲染层、注册层三道门同时关着。三道都修好之后， 真实浏览器里能看到完整的包管理卡片。

这一轮最值得留下的教训不是某一行代码，而是：31 个断言全绿和"功能能用"之间没有必然关系 —— 字符串包含测不出渲染契约，fake 对象测不出真实匹配器， 唯一可靠的办法是把边界换成真组件、真浏览器、真 --dump-config。
