2. 第 1 轮：为什么"插件装了却什么都不显示"

根因是三层串联阻断 —— 任何一层不修都看不到面板。原来的 31 个断言全绿，却一条都没覆盖到这三层。

第 1 层 · 挂载插件从未进入 cordis 配置树
patch: entry "npm-manager" not found
第 2 层 · 渲染注册的不是 React 组件
Objects are not valid as a React child
第 3 层 · 注册bundle id 与包名不一致
loaded without registering
第 1 层插件从未被挂载 —— 它连报错的机会都没有 
$ dsh --profile web --dump-config
dsh: [.../cordis.patch.yml] patch: entry "npm-manager" not found
$ grep -c 'npm-manager' dump.yml   → 0

三处配置同时错：① 插件 patch 用了顶层 - id:（非 insert 补丁要求 id 命中已存在条目， 未命中就 warn + 丢弃，不创建），且 name 填了 pnpm 的 link:./src/index.ts； ② profile 的 dsh.profile.bundles 没登记本包 → 插件的 patch 根本不会被 apply； ③ profile 自己的那段 - id: npm-manager 因 id 不存在被静默丢弃。

第 2 层注册的"组件"不是 React 组件 
// 渲染器 dsh-client-ui-renderer/lib/client.js:652
return jsx(Comp, { ...kit, ...injected, ...ownerProps });

// 旧代码注册的是返回普通对象的函数
scoped.slots.register(def, function () {
  return { render: function (props) { ... } }   // React 收到对象 → 抛错
})

而且组件读 props.target / props.dom —— slot kit 提供的是 t / renderSlot / store，没有 DOM 注入入口。

第 3 层bundle 的 id 与包名不一致 —— 最隐蔽的一层 
// dsh-client-modules/lib/client.js:248
if (!this.factories.has(id))
  throw new Error(`bundle ${url} loaded without registering "${id}"`);

id 是图行 id = 包名。旧产物写的是 id: 'npm-manager'， 而包名是 dsh-plugin-npm-manager → 必然抛错。 这一层服务端 --dump-config 全绿也照样炸，只有真实浏览器能暴露。 旁边的社区插件 @changfenhuang/dsh-annotation 源码里正好有一条注释点明这个坑。

3. 第 2 轮：从卡片到独立标签页

注册面从 settings.plugin.item（「插件 → 插件配置」里的一张卡）改为 settings.section（左侧导航里的一整页）：

ctx.slots.inject('settings.section', () => ctx.slots.register({
  name: 'settings.section',
  id: NS,                    // 'npm-manager'
  order: 37,                 // 邮箱助手 35 · 插件市场 40 → 插在两者之间
  label: () => t('nav'),     // 函数 → 可随语言切换
  locale: NS,                // 字符串命名空间 → 组件拿到 t 座位
}, NpmManagerSection))

官方渲染点是 renderSlot("settings.section", { close }, { only: active })； 导航行来自 ctx.slots.entries("settings.section") 的 {id, order, label} 并按 order 排序。 邮箱助手同样只有 section、没有卡片 —— 现在两者形态一致。

4.3 发现规则（都是写死的不变量，不做隐藏启发式）

  • 跳过 . 与 _ 前缀目录。_ 是实测得出的：本机 _dsh-uninstalled-backup-* / _backup-redesign-* 是备份， 扫它们会报出并未在用的包，属误导。
  • 跳过 node_modules / .git / dist / build / .venv / target / vendor 等。
  • 不跟随符号链接 —— withFileTypes().isDirectory() 对符号链接返回 false， 天然避免环。代价：符号链接指向的项目不会被发现。
  • 有 maxDepth（默认 3）与 limit（默认 200）兜底。

5. 第 4 轮：结果缓存

问题：全系统一次要扫 220 个包、每个都查 registry，实测几十秒。而切换范围/项目是高频操作。 方案是两层缓存，按 (scope, projectPath) 分键：

层行为
服务端listCacheTtlMs 默认 30 分钟；响应带 cached / scannedAt。 点「刷新缓存」立即作废，不看 TTL。
客户端同一 key 命中本地缓存时一个请求都不发。 只有该组合首次访问、或用户点「刷新缓存」才请求。
筛选搜索 / 仅看可升级 / 项目筛选全部是纯客户端过滤，零请求。

界面在统计行显示「数据 22:37 (缓存)」—— 你能一眼看出用的是缓存，而不是怀疑数据没刷新。

5.1 顺带修掉一个真缺陷：「刷新缓存」原本是假的

Buginvalidate() 只改时间戳，registry 缓存从没被清过

结果是 TTL 未到时点「刷新缓存」拿到的还是旧数据 —— 按钮在骗人。 现在三处缓存（结果 / 项目发现 / registry 元数据）一起作废，并新增 RegistryClient.clearCache()。

7. 顺带修掉的真缺陷

缺陷证据 / 影响
「刷新缓存」是假的 invalidate() 没清 registry 缓存 → TTL 未到时刷新后仍是旧数据
全局扫描永久跳过所有 scoped 包 if (item.startsWith('@')) continue。 实测修前 0 个（无 APPDATA）/ 2 个（有 APPDATA） → 修后两种情况都是 4 个： @colbymchenry/codegraph、@deepseek-ai/dsh、opencode-ai、pnpm
全局扫描只认 APPDATA 缺失时静默返回空。改为 NPM_CONFIG_PREFIX → APPDATA → USERPROFILE → homedir() 逐级兜底
/packages/:name 死路由 kind:'exact' 的 path 不支持 :param（exact 表是字面量 Map 查找） → 永远命中不了，请求落到 SPA fallback。改 kind:'prefix'
onClick: load 传错参数 点击事件对象被当成 load(force) 的 force（真值）→ 意外走强制刷新分支

8. 测试方法上的两处升级

1路由测试改用宿主的真实实现，不再写 fake

旧版用 fake webServer「只收集 (kind,path) 不匹配」—— 结构上就不可能发现死路由。 现在把 WebServer.prototype.register / match 借出来，用一个只有 {exact, prefixes} 的普通对象当 this：

const { WebServer } = await import(pathToFileURL(wsEntry).href)
const { register, match } = WebServer.prototype
const host = { exact: new Map(), prefixes: new Map() }
const webServer = { register: (route) => register.call(host, route) }
// 断言 match.call(host, '/plugins/npm-manager/packages/typescript') 命中 prefix 表

于是「注册唯一键检测」「exact 优先于 prefix」「最长前缀优先」全是宿主的真实语义，不是复刻。

2缓存用请求计数验证，不靠界面文本

page.on('request') 数请求数是最硬的证据；配合「数据 HH:MM 是否变化」即可证明缓存真的生效。 另外踩到两个坑：组件重新加载期间会保留上一批行（只等 rowCount > 0 会读到 stale 数据）， 所以断言要等该范围独有的标志（如统计里出现「N 个项目」）或统计文本发生变化。

10. 破坏性变更与迁移

迁移配置 scope 枚举变更

local | global | both → project | global | system，默认 project。 两处 patch 已同步迁移（scope: both → scope: project）：

  • 插件自带 cordis.patch.yml
  • profile 的 ~/.dsh/profiles/web/cordis.patch.yml

不迁移会导致 settings 注册失败（非法存量值会让整个注册挂掉，而不只是该字段回退默认）。

另有一处工具契约变更：npm_list_packages 的 scope 同步为三范围、 新增 project 参数、输出新增 5 个字段、render 从整段 JSON 改为逐行紧凑文本 （220 个包时 JSON 会淹没上下文）。

11. 剩余问题（已定位，本轮未修）

  1. npm_apply_upgrade 永久不可用：guard 读 exec.agent?.approvals?.get?.(callId)?.granted，而官方 ToolExecution 是 {callId, rootCallId, name, arguments, agent?, parent?, signal, token} —— 没有 approvals，dsh-agent 包里也搜不到。granted 恒为 undefined → 100% 被拦且用户无法批准。应改走 ctx.on('tools/pre-execute') + ctx.userQuestions.ask()。
  2. 界面上不能改配置：4 个字段仍需改 profile 的 patch。
  3. changelog 拉取：RegistryClient.getChangelog 仍返回空数组（GitHub Releases 未接）。
  4. 项目发现的边界：不跟随符号链接；跳过 _ 前缀目录（代价是 _ 开头的真实项目需用「自定义路径」访问）。
  5. vendor 快照未清理：仍带 scripts / devDependencies 与 .archive/。
