dsh-plugin-npm-manager 诊断报告
设置页为什么不显示 Web 面板

2026-09-19 · 插件 0.2.0 · dsh 0.1.5-rc.2 · profile = web · 全部结论均来自本机实测
结论：插件从未被挂载进 DSH 的配置树，所以它连"加载失败"的机会都没有。
dsh --profile web --dump-config 的合成结果里 npm-manager 出现 0 次， 同时终端打出 patch: entry "npm-manager" not found。 配置树里没有它 → 服务端 apply() 不执行 → 客户端 bundle 不被扫描 → Settings → Plugins 里自然什么都不会出现。

即使把它挂上，面板依然出不来：客户端注册的"组件"不是 React 组件，slot 渲染器会直接抛错。 这两条是串联的，必须都修。

1.1 加载器的 patch 语义（决定性）

@deepseek-ai/dsh-app-boot/lib/index.js:59 的 applyEntryPatches()——这是 DSH 唯一的 patch 语义，挂载与 --dump-config 共用同一份实现：

const target = entryMap.get(id);
if (!target) {
  warn("patch: entry %C not found", id);
  continue;            // ← 跳过。不会创建条目。
}

即：顶层 - id: X 是"改已存在的条目"，不是"新增条目"。新增必须用 - insert: [...]。而 npm-manager 这个 id 在整棵树里根本不存在（没有任何 bundle 插入过它），所以那三行配置被静默丢弃——只留一条 warn。

2. 阻断级缺陷（P0）

P0-1插件不在 dsh.profile.bundles 里，也没有以 insert 形式插入

三处配置同时错，任何一处单独修好都不够：

① ~/.dsh/profiles/web/package.json — bundles 缺项

dsh.profile.bundles 列表里有 email-assistant、dsh-mcp-skill-panel……唯独没有 dsh-plugin-npm-manager。bundle 列表是"哪些包的 dsh.bundle.patch 参与合成"的唯一入口。

② ~/.dsh/profiles/web/cordis.patch.yml — 用了 id 形式而非 insert

# 现状（无效）
- id: npm-manager
  name: dsh-plugin-npm-manager
  config: { scope: both, ... }

# 应为
- insert:
    - id: npm-manager
      name: dsh-plugin-npm-manager
      config: { scope: both, ... }

③ 插件自带的 cordis.patch.yml — 双重错误

- id: npm-manager
  name: link:./src/index.ts       ← 既无 insert（同样被跳过），
                                 name 又填了 pnpm 的 link: 规格，
                                 而且指向 TS 源码而不是构建产物 lib/

name 字段在 cordis 条目里是包名。link: 是 pnpm 的依赖协议，两者不能混用。这个 patch 即便被 insert 也解析不到任何模块。

正确对照组：email-assistant

- insert:
    - id: email-assistant
      name: email-assistant
      config: { digest: {...}, security: {...} }

并且它同时列在 dsh.profile.bundles 里。两条路都走通了，所以它能在设置页出现。

已验证修法可用（实测，未改动用户环境）

P0-2客户端注册的"组件"不是 React 组件，会被渲染器直接判死

settings.plugin.item 槽位条目的渲染路径（@deepseek-ai/dsh-client-ui-renderer/lib/client.js）：

function renderEntry(slotKey, Comp, kit, standard, injected, slotInjected, ownerProps, ...) {
  return jsx(Comp, { ...kit, ...injected, ...slotInjected.props, ...ownerProps });
}                       // Comp = entry.component，必须是 React 组件

而 client/client.js 注册进去的第二个参数是一个普通函数，返回普通对象：

scoped.slots.register({ name: 'settings.plugin.item', key: 'npm-manager', locale: {...} },
  function () {
    return { render: function (props) { ... } }   // ← React 收到一个对象
  })

React 拿到 {render: fn} 会报 Objects are not valid as a React child。即使外层不炸，内层 render 也永远不会被调用。

而且它依赖的 prop 根本不存在

var target = host.target || (host.dom && host.dom.firstChild)
if (!target) return null          // slot kit 里既没有 target 也没有 dom

slot kit 提供的标准座位是 t、renderSlot、store 等，没有任何 DOM 注入入口。这套"往 innerHTML 写字符串"的占位思路与 DSH 的 slot 契约完全不兼容。

官方写法（dshmarket，同 profile 内已验证可用）

ctx.inject(["settingsScope"], (scoped) => {
  scoped.slots.inject("settings.plugin.item", () => scoped.slots.register({
    name: "settings.plugin.item", key: NS, locale: NS, inject: () => ({ t })
  }, () => React.createElement(SettingsCard, { t, onRemoved })));
});

注意 NS 是字符串命名空间，而字典用 ctx.locale.register(NS, {zh, en}) 单独注册。

P0-3locale 传了对象，而契约要求命名空间字符串 
// 渲染器里的处理
if (entry.locale !== void 0) {
  if (face === void 0) throw new SlotAssemblyError(...);
  kit["t"] = localeSeat(face, entry.locale);      // 当作 namespace 用
}

// locale 服务的实现
bind(ns) { ... return (key, params) => this.translate(ns, key, params); }
translate(ns, key, ...) { const locales = this.dicts.get(ns); ... return key; }

传入 { en: {...}, zh: {...} } 对象后，dicts.get(对象) 必然取不到字典，t('title') 会原样返回字符串 'title'——不会崩，但界面上显示的是裸 key。属于静默失败，最难排查。

正确形态：注册条目写 locale: NS（字符串），字典走 ctx.locale.register(NS, { zh, en })。

3. 高危缺陷（P1）——挂载修好后仍然不可用

P1-1npm_apply_upgrade 被自己的 guard 永久锁死 
ctx.tools.guard((exec) => {
  if (exec.name !== 'npm_apply_upgrade') return
  const granted = exec.agent?.approvals?.get?.(exec.callId)?.granted
  if (granted) return
  return `npm 包升级是受控操作,需要用户事先批准(apply-upgrade guard)`
})

官方 ToolExecution 类型（dsh-tools/lib/types/index.d.ts:261）的字段是：

{ callId, rootCallId, name, arguments, agent?, parent?, signal, token }

没有 approvals。在整个 dsh-agent 包里也搜不到这个字段——它只出现在三个客户端包里（dsh-client-connection / dsh-client-ui-cordis / dsh-cordis-client-runner），属于 dynamic plugin 的专用面，普通 static 插件的 exec 上不存在。

后果：granted 永远是 undefined → guard 永远返回拒绝理由 → 四个工具里有一个 100% 不可用，且用户没有任何途径批准。这是 conformance 技能 §8.1 点名的反模式（"某个功能 100% 不可用"）。

正确做法

ctx.on('tools/pre-execute', async (exec, next) => {
  if (exec.name !== 'npm_apply_upgrade') return next()
  const answer = await ctx.userQuestions.ask({ ... })   // 真实可询问的服务
  return answer ? next() : { reason: '用户取消' }
})

参考实现：@deepseek-ai/dsh-tool-ask-user/lib/index.js:97。

P1-2路由 #2 是死路由——kind: 'exact' 不支持 :param 
ctx.webServer.register({
  kind: 'exact',
  path: '/plugins/npm-manager/packages/:name',   // 永远不会被命中
  handler: ...
})

webServer 的匹配逻辑（dsh-host-webserver/lib/index.js:322）：

match(pathname) {
  const exact = this.exact.get(pathname);        // 字面量 Map 查找，无模式匹配
  if (exact) return exact;
  for (const [prefix, route] of this.prefixes) {
    if (pathname !== prefix && !pathname.startsWith(`${prefix}/`)) continue;
    ...
  }
}

exact 表是纯字面量查找，:name 会被当成普通字符。真实请求 /plugins/npm-manager/packages/typescript 既命中不了 exact，也没有对应 prefix，最终落到 SPA fallback，返回一个 HTML 页面而不是 JSON。

对照 dshmarket 的 30+ 条路由：全部是 kind:'exact' + 无参数扁平路径。这是实际约定。

修法

ctx.webServer.register({
  kind: 'prefix',
  path: '/plugins/npm-manager/packages',   // exact 表先查，#1/#3 仍优先
  handler: async (req, res) => { /* 复用现有的 regex 解析 */ }
})

handler 里已有的 url.pathname.match(/^\/plugins\/npm-manager\/packages\/(.+)$/) 可以直接复用，只需补一个"裸 /packages 由 #1 处理"的分支。

P1-3settings 服务用了模块级 inject，而非 ctx.inject 降级边界 
export const inject = ['tools', 'webServer', 'settings']

dshmarket 的 lib/settings.js 里有一段专门解释为什么不能这么写：settings 服务在旧 host 上可能不存在，模块级 inject 会让 entry 永久 pending；正确做法是 ctx.inject(['settings'], cb)——"the graceful-degradation boundary: on a host with no settings service the callback never runs and the composed entry stands"。

本 profile 装了 @deepseek-ai/dsh-settings（配置树里 - id: settings / @deepseek-ai/dsh-settings-file），所以不是当前故障原因，但属于契约偏差，换 profile 就会踩。

4. 次要问题（P2）

项问题建议
dsh.client.inject 只声明了 @deepseek-ai/dsh-client-locale，但代码依赖 settingsScope，其提供方是 @deepseek-ai/dsh-client-ui-settings。对照 dshmarket 声明了 3 个包。 补 @deepseek-ai/dsh-client-ui-settings；若走 React 路线还需 @deepseek-ai/dsh-client-ui-primitives。
scope.dispose?.() settings.register() 返回的 scope 只有 get / watch / update / replace，没有 dispose。这行是死代码（回收靠 fiber effect，不算错）。 删掉，或改为显式说明依赖 fiber 生命周期。
vendor 快照 package.json 仍带 scripts: { build: "tsc", test: ... }。当前无 prepare 所以不致命；一旦将来加 prepare，pnpm install 会在快照里跑 tsc，而快照没有 tsconfig.json 和 src/，直接失败（conformance §14.2.1）。 部署脚本自动剥离 scripts 与 devDependencies。DEPLOY.md 里写了这段脚本，但显然没执行。
vendor 快照内容 带进了 .archive/（round1-11 的 30 个文件）、_strip-*.mjs、_archive-old-src.mjs、PLAN.round1-11.archive.md。 部署时按 files 白名单拷贝，或补一份 .npmignore。
客户端构建链 scripts/build-client.mjs 是纯占位（三行 console.log）；client/client.js 是手写占位。"第 3 轮接真 React 构建链"从未发生。 见第 6 节路线。
DEPLOY.md 部署清单里没有"把插件加进 dsh.profile.bundles"这一步；6.3 节还写着"patch 已经由本项目的 cordis.patch.yml 提供"——这正是本次错误的来源。 补 bundles 步骤 + 把 cordis.patch.yml 改成 insert 形式。

5. 为什么 31 个测试全绿却什么都没测出来

项目自测 31/31 通过，但上面每一条 P0/P1 都逃过了：

测试实际断言漏掉了什么
tests/client-verify.mjs 字符串包含检查（includes('return module.exports')）+ vm 里跑一遍确认 factory 返回对象。 完全没有触碰 slot 渲染器。它证明了"文件能加载"，但"组件是 React 组件"这件事一个字都没测。
tests/routes-verify.mjs 用 fake webServer 收集 register() 的调用，检查 (kind,path) 不重复、handler 是函数。 fake 的 register 只 push 不匹配。所以 :name 能不能命中这条，测试结构上就不可能发现——真匹配器是宿主那个 match(pathname)。
scripts/dev-conformance-check.mjs 4 层 schema 校验（这个做得很好，用的是宿主真包）。 schema 之外的契约（挂载、路由匹配、React、approval）不在覆盖范围内。

这是 conformance 技能 §13.1 说的"mock 测试 ≠ 验证"：内联重写一遍实现逻辑的测试，验证的是"我以为的行为"，不是"真实代码的行为"。修的方向不是加断言数量，而是把边界换成真实对象：

// routes：用宿主的真匹配器，而不是自己 push
import { match } from '@deepseek-ai/dsh-host-webserver'  // 或实例化真 Router
assert(match('/plugins/npm-manager/packages/typescript') !== undefined)

// client：把注册进来的 Component 真的交给 React 渲染一次
renderToString(React.createElement(entry.component, { t: k => k }))

6. 修复清单（按依赖顺序）

第 1 步 — 让它先能被挂载（5 分钟，改 2 个文件）

  1. 插件自己的 cordis.patch.yml：改成 - insert: [{ id: npm-manager, name: dsh-plugin-npm-manager, config: {...} }]。
  2. ~/.dsh/profiles/web/package.json：把 dsh-plugin-npm-manager 加进 dsh.profile.bundles（与 email-assistant 并列）。
  3. ~/.dsh/profiles/web/cordis.patch.yml：要么删掉那段无效的 - id: npm-manager（由第 1 步的 bundle patch 接管），要么就地改成 - insert: 形式。
  4. 验证：dsh --profile web --dump-config | grep -A3 npm-manager 应能命中。

只做这一步的结果：服务端 4 个工具、5 条路由会活过来（agent 对话里可以调 npm_list_packages），但 设置页仍然是空的——因为 P0-2。

第 2 步 — 让面板真的渲染（半天）

  1. 建 client/src/index.tsx，写真正的 React 组件（卡片 + 包列表 + 刷新按钮），通过 fetch('/plugins/npm-manager/packages') 打后端。
  2. 用 tsdown / rolldown 打包成单文件 client/client.js（照抄 dshmarket 的 build:client 链路）。
  3. package.json 补 dsh.client.inject：["@deepseek-ai/dsh-client-locale", "@deepseek-ai/dsh-client-ui-settings"]。
  4. 字典改走 ctx.locale.register(NS, { zh, en })，注册条目里写 locale: NS（字符串）。
  5. 组件必须是 React.createElement(...) 或 JSX 编译产物，绝不能返回普通对象。

第 3 步 — 补齐功能正确性

  1. approval 改走 ctx.on('tools/pre-execute') + ctx.userQuestions.ask()（P1-1）。
  2. 路由 #2 改 kind: 'prefix'（P1-2）。
  3. inject 里的 settings 换成 ctx.inject(['settings'], cb)（P1-3）。
  4. 测试从"字符串/fake 断言"升级为"真实匹配器 + 真实 React 渲染"（第 5 节）。
  5. 更新 DEPLOY.md：补 bundles 步骤，删掉"patch 已由本项目提供"的错误说法。

7. 一句话总结

面板不显示，第一因是部署配置错了（插件从未进入配置树，只留一条 warn）， 第二因是客户端面板的写法从根上不符合 DSH 的 slot 契约（不是 React 组件 + locale 传对象）。 前者 5 分钟可修，后者需要把 build-client.mjs 那条从未落地的 React 构建链真正做出来。 现有 31 个测试全绿，但它们没有一条覆盖到这两处。
